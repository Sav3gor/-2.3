# Звіт із практичної роботи КП 2.9

## Тема, мета та вихідний стан

**Тема:** централізоване керування станом PWA-застосунку TaskFlow через Pinia: завдання, проєкти, фільтри та обчислювана статистика.

**Мета:** підключити Pinia до Vue 3, створити stores із state/getters/actions, застосувати storeToRefs(), організувати взаємодію сховищ та синхронізацію сторінок.

Роботу виконано в тому самому TaskFlow, що й КП 2.8. Початковий застосунок підтримував CRUD завдань, пошук у назві й описі, комбіновані фільтри, сортування, підтверджене видалення, категорії, preview і статистику. Наявні маршрути та компоненти Framework7 збережено. Десять демонстраційних завдань залишаються у src/data/tasks.js.

Технології: Vue 3, Pinia, @vue/devtools-api, Framework7, JavaScript, Vite та PWA. Pinia не є постійним сховищем: після reload дані та критерії повертаються до початкових. IndexedDB у цій роботі не реалізується.

## Reactive-модуль і Pinia

Попередній модуль експортував один reactive-об’єкт taskState та окремі функції. Нове сховище визначено через defineStore('tasks', ...). Pinia задає стандартну організацію state/getters/actions, підтримує окремі екземпляри для тестів та інтеграцію з Devtools. Старі глобальні експорти taskState замінено useTasksStore().

**state** містить вихідні дані. **getters** обчислюють похідні значення без зміни state. **actions** виконують валідацію та зміни. **storeToRefs()** повертає реактивні посилання на state/getters, щоб деструктуризація не створювала нерухомих копій значень.

```js
const app = createApp(App)
app.use(createPinia())
registerComponents(app)
app.mount('#app')
```

Framework7.use(Framework7Vue), стилі Framework7, іконки та registerComponents(app) збережено. Pinia підключається до того самого Vue-застосунку перед його монтуванням.

## Сховище завдань

**useTasksStore** містить tasks, searchText, selectedStatus, selectedPriority, selectedProject, sortOrder, onlyIncomplete і withoutDueDate. Початкові записи отримують projectId='general' і попередню категорію, не змінюючи data/tasks.js.

Getters: totalTasks, completedTasks, progressTasks, plannedTasks, completionPercent, activeTasks, visibleTasks та visibleCompletionPercent. Видимий список об’єднує текст, статус, пріоритет, проєкт, невиконані та відсутність терміну логічним AND. Пошук і всі режими сортування КП 2.8 збережено. Sort застосовується тільки до копії після filter().

Actions: addTask(), updateTask(), deleteTask(), setTaskStatus(), setTaskPriority(), resetFilters() та startCurrentProjectTasks(). Збережено перевірки довжин, календарних дат, допустимих значень і унікальності назви нового завдання. Невідомий projectId нормалізується до general. Нова назва завдання має 3–80 символів, опис — до 500, дата необов’язкова.

```js
const taskStore = useTasksStore()
const {
  tasks, visibleTasks, selectedProject, searchText,
} = storeToRefs(taskStore)
```

Фільтри належать Pinia, тому перевідкриття сторінки без reload не скидає їх. Кнопка «Скинути фільтри» очищує всі критерії та повертає режим newest. Відкриття форми, editingId, поточний вибір картки та назва створюваного проєкту залишаються локальними ref().

## Сховище проєктів та взаємодія

**useProjectsStore** має projects та nextProjectId. Початкові проєкти: «Загальні», «Навчання», «Особисті». addProject() повертає новий об’єкт або null, перевіряє назву 3–40 символів, прибирає крайні пробіли й не допускає дублювання без урахування регістру. IDs створюються локальним лічильником project-1, project-2 тощо.

Getters projectCount і projectTitle(id) повертають кількість та назву. Getter projectStats читає завдання через useTasksStore() і обчислює для кожного проєкту total, completed, incomplete та completionPercent. Порожній проєкт має 0%.

```js
const completed = projectTasks.filter(task => task.status === 'done').length
const completionPercent = projectTasks.length
  ? Math.round(completed / projectTasks.length * 100)
  : 0
```

Перенесення projectStats до store усуває дублювання на HomePage і TasksPage та дає одне правило розрахунку. Недоліки — залежність projects-store від tasks-store та необхідність уникати циклів обчислення. Тут міжсховищні звернення відбуваються лише у getters/actions; state не читає інше сховище під час створення.

## Компоненти і сторінки

TaskForm отримує список проєктів через Props, показує селектор і перевіряє, що вибір існує. Під час створення початковий проєкт береться з активного фільтра або general. Форма має власну копію полів; save передає projectId, cancel не змінює вихідний запис.

TaskListControls залишається незалежним від stores: отримує projects, project, withoutDueDate та інші Props, генерує update:project, update:withoutDueDate й попередні події. TasksPage зв’язує їх із storeToRefs через v-model.

TaskCard отримує projectTitle від сторінки, не імпортує store й не змінює Props. CRUD, edit/delete/status/priority/task-select події збережено. HomePage використовує getters для загальної статистики й актуальних карток, а також відображає проєкти з кількістю невиконаних та відсотком виконання.

На TasksPage додано «Мої проєкти», створення назви з повідомленням про помилку, проєктні лічильники та фільтр. Успішне створення проєкту автоматично вибирає його у фільтрі. Форми, каталог і фільтри мають адаптивні CSS-правила для вузьких екранів.

## Додаткові завдання

1. Написано projectStats у projects-store замість локального дубльованого computed; переваги та залежності пояснено вище.
2. Додано на HomePage окремий проєктний блок із кількістю невиконаних без копіювання масиву завдань.
3. Додано відсоток виконання на обох сторінках; для порожнього проєкту — 0%.
4. Написано action startCurrentProjectTasks(). Він працює тільки для конкретного selectedProject і переводить усі його завдання у progress, незалежно від інших умов списку. Сторінка окремо запитує підтвердження з назвою проєкту. За вибору «Усі проєкти» кнопка недоступна.
5. Додано «Лише без терміну» до Pinia state, visibleTasks, інтерфейсу та скидання умов.
6. Перевірка через Vue Devtools / Pinia та скріншот списку stores ще не виконані. Потрібно відкрити dev-версію із Vue Devtools, показати stores tasks і projects, викликати action та зафіксувати зміну state. Програмний тест $onAction пройшов і підтвердив виклик групової action, але він не замінює фактичну перевірку Devtools.

## Перевірки і фактичний стан

Встановлено pinia 4.1.0 і @vue/devtools-api 8.2.1. Команда npm test завершилась успішно: 16 перевірок пройдено, помилок немає. npm run build також успішна: оброблено 336 модулів, створено production-ресурси, manifest і service worker. Vite повідомляє про JS-чанк понад 500 kB; це попередження не зупинило збірку.

Тести монтують справжні Vue-компоненти у тестовому renderer, використовують справжню Pinia та підмінюють оболонки Framework7 і відповідь window.confirm. ## Контрольні запитання

1. **Стан застосунку** — поточні завдання, проєкти та умови відображення. Централізація забезпечує узгоджені дані й правила змін для всіх компонентів.
2. **Pinia і reactive().** Pinia організовує стан у stores зі стандартними getters/actions, інструментами тестування та Devtools. reactive() сам по собі надає лише реактивний об’єкт.
3. **createPinia().** Створює кореневий екземпляр керування станом; його підключають через app.use() у main.js перед app.mount().
4. **registerComponents(app).** Реєструє f7-app, f7-view, f7-page та інші компоненти; його видалення може зламати інтерфейс Framework7.
5. **Option Store.** defineStore('id', { state: () => ({}), getters: {}, actions: {} }).
6. **State/getters/actions.** tasks — state; totalTasks і visibleTasks — getters; addTask() і deleteTask() — actions.
7. **storeToRefs().** Повертає refs для реактивної деструктуризації state/getters. Звичайне присвоєння примітивного значення зі store не зберігає його зв’язок із майбутніми змінами.
8. **Getter і action.** Getter обчислює значення; action змінює стан або виконує бізнес-операцію й може бути асинхронним.
9. **Локальні showForm/editingId.** Це стан лише одного інтерфейсу форми, який не потрібний іншим сторінкам.
10. **Спільне сховище.** Компоненти викликають ту саму useStore() з одним підключеним екземпляром Pinia та отримують той самий store.
11. **Окремий projects-store.** Відокремлює каталог і перевірку назв проєктів від CRUD завдань та полегшує підтримку.
12. **Перевірка projectId.** Форма перевіряє наявність у списку; action нормалізує невідомий ID до general.
13. **Fallback general.** Дає старим завданням коректну проєктну прив’язку без редагування початкового масиву.
14. **Чому не сортують tasks напряму?** sort() змінює порядок на місці; getter має сортувати окремий масив після filter().
15. **Поєднання фільтра проєкту.** Порівняння projectId входить через AND до умов тексту, статусу, пріоритету та швидких фільтрів.
16. **Схема взаємодії.** TaskCard отримує Props, генерує подію з ID; TasksPage викликає action; Pinia оновлює state; getters і шаблони реактивно перераховуються.
17. **Зникнення проєктів після reload.** Каталог живе лише в пам’яті; state створюється заново з початкових значень.
18. **IndexedDB.** Дасть постійне локальне зберігання структурованих даних і використання цих даних без мережі.
19. **npm run build.** Перевіряє production-компіляцію, імпорти й створення ресурсів; dev-сервер не замінює перевірку production-збірки та поведінки користувацьких сценаріїв.
20. **Масштабування.** Єдині actions і getters зменшують дублювання, ізолюють правила, спрощують тестування, Devtools та подальше підключення постійного сховища.

## Висновки та джерела

Підготовлено перехід TaskFlow на два Pinia stores зі спільними критеріями, статистикою та каталогом проєктів. Реалізовано п’ять додаткових функціональних пунктів; усі 16 автоматичних перевірок і production build успішні. Для повного оформлення роботи залишилися фактична перевірка Devtools, браузерна перевірка адаптивності та скріншоти.

Офіційні матеріали: https://pinia.vuejs.org/getting-started.html та https://pinia.vuejs.org/cookbook/composing-stores.html. Репозиторій проєкту: https://github.com/Sav3gor/-2.3.
