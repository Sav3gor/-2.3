# Звіт із практичної роботи КП 2.10

## Тема, мета та вихідний стан

**Тема:** локальне постійне зберігання завдань і проєктів TaskFlow засобами IndexedDB з інтеграцією до Pinia.

**Мета:** спроєктувати браузерну базу, виконувати асинхронні транзакції, відновлювати стан до монтування інтерфейсу, автоматично зберігати зміни та перевіряти стійкість до збоїв.

Роботу виконано в наявному TaskFlow на Vue 3, Framework7, Vite та Pinia. Після КП 2.9 застосунок мав CRUD завдань, проєкти, прив’язки, спільні фільтри, сортування, статистику й групову дію. Ці можливості збережено. Проблема попередньої версії: стан Pinia існував лише в пам’яті й втрачався після reload. Тепер завдання, проєкти та лічильник IDs зберігаються локально.

Використано idb 7.1.1, який надає Promise-інтерфейс до IndexedDB. Дані прив’язані до origin, браузера та його профілю. Серверного обміну та синхронізації між пристроями немає.

## Архітектура та структура файлів

```text
Vue / Framework7
  → actions Pinia (tasks, projects)
  → $subscribe()
  → persistence.js
  → database.js (idb)
  → IndexedDB taskflow-db

Завантаження:
IndexedDB → readSnapshot() → validateSnapshot()
  → $patch() обох stores → підписки → app.mount()
```

П’ять основних нових/оновлених файлів методички: services/database.js — схема та транзакції; services/persistence.js — hydration, підписки, черга та помилки; main.js — відновлення до mount; TasksPage.vue — статус і повторна спроба; css/persistence.css — оформлення повідомлень.

Додатково створено services/snapshot.js для валідації резервних копій, pages/SettingsPage.vue та маршрут /settings/. Додатковий маршрут не змінює наявні /, /tasks/ і /about/. App.vue, stores tasks/projects, data/tasks.js, HomePage, AppTabbar, TaskCard, TaskForm, TaskListControls і PWA-конфігурацію не змінено.

```text
my-app/src/

  main.js
  routes.js
  pages/
    TasksPage.vue
    SettingsPage.vue

my-app/tests/

```

## Схема IndexedDB

База taskflow-db має версію 1. Обробник upgrade() створює відсутні сховища.

| Сховище | Ключ | Поля / службові значення | Призначення |
| --- | --- | --- | --- |
| tasks | keyPath id, число | id, title, description, status, priority, dueDate, projectId, category | Завдання й прив’язки |
| projects | keyPath id, рядок | id, title | Каталог проєктів |
| metadata | явно заданий рядковий ключ | initialized, nextProjectId, lastSavedAt | Перший запуск, лічильник і час запису |

initialized=true відрізняє нову базу від збереженого порожнього списку. Після видалення всіх завдань список tasks залишається порожнім, але прапорець зберігається, тому демонстраційні записи не повертаються. nextProjectId відновлюється з metadata та перевіряється за найбільшим project-N, щоб не повторити ID.

## Транзакції та snapshot

getDatabase() повторно використовує одне з’єднання. readSnapshot() читає всі дані однією readonly-транзакцією. writeSnapshot() виконує clear() для tasks/projects, ставить у чергу put() поточних записів і службових значень та очікує tx.done. Усі операції належать одній readwrite-транзакції.

```js
const tx = db.transaction(['tasks', 'projects', 'metadata'], 'readwrite')
requests.push(tasks.clear(), projects.clear())
for (const task of snapshot.tasks) requests.push(tasks.put(task))
for (const project of snapshot.projects) requests.push(projects.put(project))
await Promise.all([...requests, tx.done])
```

Транзакція атомарна: якщо запис не вдається, очищення й часткові вставки відкочуються. У catch транзакцію перериваємо, а її Promise та вже створені запити очікуємо через Promise.allSettled(). У середині транзакції немає сторонніх мережевих запитів або довгих await.

Повний snapshot простіший для невеликого навчального списку й узгоджує обидва stores, але переписує всі записи. Точкові put/delete ефективніші для великих даних, проте потребують окремого відстеження змін та узгодження пов’язаних записів.

## Hydration, підписки та черга

main.js створює Vue і Pinia, зберігає Framework7.use() і registerComponents(), очікує initializePersistence(pinia), після чого монтує інтерфейс. Верхньорівневого await немає — використано async bootstrap().

Якщо initialized відсутній, записується початковий snapshot один раз. Якщо він є, увесь знімок перевіряється перед $patch() обох stores. Лише після відновлення під’єднуються $subscribe() із detached:true та flush:'sync'. Якщо читання або перевірка даних не вдалися, застосунок працює з тимчасовим станом і не вмикає автоматичний запис, щоб не перезаписати існуючу базу.

```js
const current = JSON.stringify(snapshot())
if (!force && current === fingerprint) return
fingerprint = current
revision += 1
```

Порівняння охоплює тільки tasks, projects та nextProjectId. Пошук, фільтри й сортування не входять до snapshot, тому не викликають зайвих транзакцій. Синхронні зміни об’єднуються мікрозадачею. Поки триває запис, нові зміни збільшують revision і записуються наступною ітерацією послідовної черги.

## Стан збереження та помилки

persistenceState має status loading/saving/saved/error, error, canRetry та lastSavedAt. «Усі зміни збережено» показується тільки після успішного завершення транзакції. Час lastSavedAt записується у metadata та відновлюється в наступному сеансі.

За помилки запису нові дані залишаються в Pinia, попередня база не замінюється частково, з’являється «Повторити збереження». Повторна спроба записує актуальний стан. Після помилки відкриття/читання canRetry=false: автоматичний запис вимкнений до коректного нового запуску.

Перед reload або закриттям вкладки слід дочекатися повідомлення про завершення запису. Browser IndexedDB є локальним сховищем і може бути очищена разом із даними сайту; для незалежної копії додано JSON-експорт.

## Додаткові завдання

1. **Експорт JSON.** Кнопка формує файл із tasks, projects, nextProjectId, версією формату й exportedAt. До експорту потрапляють тільки дозволені поля завдань та проєктів.
2. **Імпорт JSON.** Перевіряються структура, типи, допустимі значення, дати, унікальність IDs і назв проєктів, наявність базового general та всі посилання projectId. Некоректний файл не змінює стан. Обмеження розміру — 5 МБ. Перед заміною всіх даних запитується підтвердження. Імпорт дозволений тільки після успішної ініціалізації бази; після нього закривається форма та скидаються фільтри.
3. **Точкове видалення.** У database.js є deleteRecord(storeName,id), що викликає delete() й очікує завершення транзакції. Це окрема навчальна функція; основний CRUD залишається на узгодженому snapshot, щоб наступний запис Pinia не повернув видалений напряму запис.
4. **Час збереження.** metadata.lastSavedAt відображається біля статусу та на сторінці налаштувань. Помилка нового запису не підмінює час останнього успіху.
5. **Налаштування.** Маршрут /settings/ читає count() завдань/проєктів і метадані безпосередньо з IndexedDB, має кнопку оновлення та повідомлення про помилку. Посилання доступне в Navbar вкладки завдань.
6. **Дві вкладки.** Фактичний браузерний тест ще не виконано. Можливий конфлікт: обидві вкладки відновили один snapshot, потім останній запис однієї замінить зміни іншої. Транзакція захищає атомарність, але не запобігає втраті змін між сеансами. Можливе рішення: metadata.revision із перевіркою у транзакції, BroadcastChannel для сповіщення інших вкладок, повторне читання або явне вирішення конфлікту. BroadcastChannel не реалізовано; серверної чи міжвкладкової синхронізації не заявлено.

## Перевірки та фактичні результати

Регресійні тести КП 2.5–2.9 перевіряють інтерфейс і справжню Pinia в тестовому renderer. Нові тести контролера використовують асинхронний адаптер зберігання в пам’яті для контрольованих збоїв і затримок; вони не є браузерним тестом IndexedDB. Для інтеграційного тесту зі справжнім idb потрібен fake-indexeddb.

На момент оформлення 16 регресійних та 8 нових тестів пройшли; інтеграційний тест IndexedDB пропущено, оскільки fake-indexeddb не встановлено. Production build успішний. Після встановлення тестового пакета потрібно повторити інтеграційну перевірку та оновити цей результат.

| --- | --- | --- | --- | --- |

Натискання F5 у реальному браузері, вкладки DevTools та офлайн-запуск ще не перевірялися.

## Контрольні запитання

1. **Локальне постійне зберігання** — запис даних у браузері так, щоб вони були доступні після завершення поточного сеансу.
2. **Pinia після reload.** За замовчуванням її state є оперативною пам’яттю й створюється заново.
3. **IndexedDB і localStorage.** IndexedDB асинхронна, підтримує об’єкти, транзакції та індекси; localStorage синхронне рядкове сховище ключ–значення.
4. **Origin.** Поєднання схеми, хоста й порту; різні origins мають окремі бази.
5. **upgrade().** Створює або змінює схему при першому відкритті чи підвищенні версії.
6. **keyPath id.** Первинний ключ береться з поля id; для завдань це число, для проєктів — рядок.
7. **metadata.** Зберігає initialized, лічильник проєктів і час успішного запису.
8. **initialized.** Відрізняє нову базу від навмисно порожнього набору завдань.
9. **Видалення всіх завдань.** За initialized=true відновлюється порожній tasks без демонстраційних записів.
10. **readonly/readwrite.** Перший режим читає дані, другий дозволяє змінювати їх у транзакції.
11. **getAll/put/clear.** Читають усі записи, створюють або замінюють запис за ключем, очищують сховище відповідно.
12. **Атомарність.** Усі операції транзакції або завершуються разом, або відкочуються.
13. **tx.done.** Promise завершення всієї транзакції, а не окремого запиту.
14. **Сторонні await.** Можуть дозволити браузеру закрити неактивну транзакцію до постановки наступних запитів.
15. **Hydration.** Відновлення Pinia зі збережених даних; до mount запобігає показу тимчасових демонстраційних записів.
16. **$patch().** Узгоджено переносить прочитані масиви й лічильник у реактивний store.
17. **$subscribe().** Сповіщає про зміни state, після яких контролер перевіряє потребу в записі.
18. **Пошук не зберігаємо.** Він не змінює завдання або проєкти; його запис створював би зайві транзакції.
19. **Послідовність записів.** Один активний Promise запису, лічильники revisions і цикл для наступних змін.
20. **Підтвердження після транзакції.** До її завершення запити ще можуть відкотитися; раннє saved було б хибним.
21. **IndexedDB недоступна.** UI запускається з тимчасовими даними й помилкою; автоматичний запис вимкнений, щоб не знищити існуючу базу.
22. **Дві вкладки.** Старий snapshot однієї може перезаписати нові зміни іншої; потрібні перевірка revision, сповіщення та узгодження.
23. **IndexedDB і офлайн-запуск.** Вона зберігає дані, але не забезпечує завантаження HTML, JS і CSS без мережі.
24. **Service Worker.** Кешує оболонку застосунку та обробляє запити для запуску PWA без мережі.
25. **Чутливі дані.** Паролі, токени й секретні ключі не слід зберігати без спеціального захисту; доступ має код відповідного origin.
26. **Snapshot і точкові операції.** Snapshot простий та узгоджений для невеликих обсягів, але переписує всі записи; put/delete економніші, проте складніші для синхронізації пов’язаних змін.

## Висновки

У роботі реалізовано постійне локальне зберігання TaskFlow. Створено базу taskflow-db зі сховищами tasks, projects і metadata. Pinia залишається поточним реактивним станом, а IndexedDB зберігає його між сеансами. Контролер відновлює дані перед показом інтерфейсу та автоматично записує зміни. У тестах контролера створені й відредаговані записи відновлюються в новому сеансі. Видалення всіх завдань не запускає повторне створення демонстраційних даних. Перевірено відновлення після помилки запису та послідовне виконання швидких змін. Одна транзакція забезпечує атомарність повного знімка; фактичну інтеграцію IndexedDB потрібно перевірити окремо. Зберігання обмежене origin і профілем браузера та не синхронізує пристрої або вкладки. Офлайн-запуск залежить від активного Service Worker і кешу оболонки. Подальший розвиток — перевірка конфліктів revisions, BroadcastChannel та інтеграційні браузерні тести.
